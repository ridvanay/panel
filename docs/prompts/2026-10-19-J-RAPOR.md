## CMS'te TR/EN sayfa yapısı
- **Tek tablo, ayrı çeviri tablosu yok.**
  - Varsayılan dilin (`Locale.isDefault`) içeriği `Page.title` ve `Page.blocks` kanonik kolonlarında durur.
  - Diğer dillerin içeriği `Page.translations` JSON'unda, dil koduyla tutulur: `{ "en": { title, blocks, slug?, seoTitle?, ... } }`.
- **Dil başına slug** `ContentSlug` tablosunda (`syncContentSlugs`). Çevirinin `title`'ı doluysa o dil için slug satırı oluşur; çeviride `slug` yoksa kanonik slug kullanılır.
- **İçerik biçimi:** Sayfa builder blokları (JSON). Script her sayfayı iki bloğa çevirir: `heading` (h1, başlık) ve tek `text` bloğu (HTML; `sanitizePageBlocks` ile temizlenir).
- **`isLegalDocument=true` sayfalarda sessiz çeviri yedeği yok.** EN çevirisi yoksa EN istekte içerik boş döner. Bu yüzden iki dil birlikte yüklenir.
- **Hangi dil kanonik kayda gider? Script bunu `Locale.isDefault`'a göre seçer.**
  - Varsayılan **TR** ise TR kanonik kayda, EN `translations.en`'e yazılır (prompttaki varsayım).
  - Depoda `scripts/switch-default-locale-to-en.ts` var. Canlıda varsayılan **EN** yapıldıysa tersi uygulanır: EN kanonik, TR `translations.tr`. Aksi hâlde TR metin EN URL'de görünürdü.
  - Kuru çalışmanın ilk satırı hangisinin geçerli olduğunu yazdırır.
- **Korunanlar:** slug, `isLegalDocument`, `status`/`publishedAt`, SEO alanları, menü/footer (`NavigationItem`'a dokunulmaz) ve çeviri JSON'undaki diğer alanlar (ör. özel EN `slug`). Yalnızca başlık ve bloklar değişir. Yeni sayfa açılmaz; slug bulunamazsa script durur.
- **Markdown → HTML:** Projede markdown kütüphanesi yok ve paket eklenmedi. Metinlerde kullanılan alt küme kendi küçük dönüştürücüyle işleniyor:
  - `##`/`###` başlık, paragraf, `- ` liste, `1. ` liste, `> ` alıntı, `**kalın**`, `*italik*`, `[metin](https|mailto)`.
  - Önce HTML kaçışı yapılır. Güvenli olmayan link şemaları bağlantıya dönüşmez.
  - Ardından `PageBlockListSchema` + `sanitizePageBlocks` uygulanır.

## Scriptin kullanımı
**Yerel (backend/ dizininden):**
```bash
# 1) Kuru çalışma (varsayılan, hiçbir şey yazmaz): mevcut/yeni başlık ve uzunluk, EN kaydı var mı, eksik yer tutucular
npx tsx scripts/publish-legal-pages.ts

# 2) Gerçek yükleme (values.json dolu ve hukuk onaylı olmalı)
npx tsx scripts/publish-legal-pages.ts --confirm=publish-legal --operator="Ad Soyad"

# 3) Geri dönüş (yüklemenin yazdırdığı yedek dosyasıyla)
npx tsx scripts/publish-legal-pages.ts --restore=backups/legal-pages-<zaman>.json --confirm=restore-legal --operator="Ad Soyad"
```

**Gerçek yüklemenin adımları:**
1. Mevcut 4 sayfanın tam hâli (TR + EN) `backups/legal-pages-<zaman>.json` dosyasına yazılır (dosya 0600, klasör 0700, `.gitignore`'da).
2. Dört sayfa, ContentSlug senkronu ve `cms.legal_pages.published` audit kaydı **tek transaction**'da yazılır. Audit kaydında operatör, işletim sistemi kullanıcısı, hostname, slug listesi ve yedek dosyası adı bulunur.
3. Plan alındıktan sonra bir sayfa başka biri tarafından değiştirildiyse hiçbir şey yazılmaz.
4. Son olarak yayındaki sayfalar için mevcut ISR yenilemesi (`triggerPublicPageRevalidation`) tetiklenir.

**Güvenlik kuralları:**
- **Eksik/boş yer tutucu varsa gerçek yükleme reddedilir.** Kuru çalışma yine çalışır ve eksikleri listeler.
- **Çeviri dili (EN) etkin değilse gerçek yükleme durur.** Bilerek yüklemek için `--allow-disabled-locale` gerekir.
- **Geri dönüş:**
  - Önce mevcut hâlin yedeğini alır.
  - Yalnızca bu dört slug'ı kabul eder; yedekteki bloklar ve çeviriler doğrulanıp sanitize edilir.
  - `cms.legal_pages.restored` audit kaydı yazar.

**Seçenekler:** `--dir` (varsayılan `../docs/legal`), `--backup-dir` (varsayılan `backups`), `--no-revalidate`, `--allow-disabled-locale`.

**Sunucuda (prod imajı; repo kökünden).** Konteyner root olmayan kullanıcıyla çalışır ve `/app` altında klasör açamaz. Bu yüzden `docs/legal` doğrudan `/app/legal`'a kopyalanır; yedekler yazılabilir olan `storage/legal-backups`'a gider.
```bash
docker compose cp backend/scripts backend:/app/scripts
docker compose cp backend/src backend:/app/src
docker compose cp backend/tsconfig.json backend:/app/tsconfig.json
docker compose cp docs/legal backend:/app/legal
# kuru çalışma
docker compose exec -T backend sh -c "cd /app && npx -y tsx@4.23.1 scripts/publish-legal-pages.ts --dir=legal --backup-dir=storage/legal-backups"
# gerçek yükleme
docker compose exec -T backend sh -c "cd /app && npx -y tsx@4.23.1 scripts/publish-legal-pages.ts --dir=legal --backup-dir=storage/legal-backups --confirm=publish-legal --operator='Ad Soyad'"
# yedeği konteynerden dışarı al (konteyner yeniden oluşturulunca silinir)
docker compose cp backend:/app/storage/legal-backups ./legal-backups-<tarih>
# geri dönüş
docker compose exec -T backend sh -c "cd /app && npx -y tsx@4.23.1 scripts/publish-legal-pages.ts --restore=storage/legal-backups/legal-pages-<zaman>.json --confirm=restore-legal --operator='Ad Soyad'"
# iş bitince kopyaları temizle
docker compose exec -T -u root backend sh -c "rm -rf /app/scripts /app/src /app/tsconfig.json /app/legal"
```
Windows Git Bash'ten çalıştırırken `MSYS_NO_PATHCONV=1` kullanın.

Bu yöntem **yerel backend konteynerinde denendi.** Script prod imajında yüklenip çalıştı: yerel DB'de bu sayfalar olmadığı için beklendiği gibi "Sayfa bulunamadı … işlem durduruldu" dedi. `storage/` yazılabilir. Kopyalanan dosyalar sonra temizlendi.

## İş 3 — "Aydınlatma Metni" linkleri
- **İletişim formu (`contact-form.tsx`):** Link artık `form.consentLegalPage`'i körü körüne kullanmıyor.
  - Admin'in seçtiği sayfa KVKK/aydınlatma kalıbına uyuyorsa o kullanılır.
  - Uymuyorsa yayınlanmış yasal sayfalar arasından sıkı `resolveKvkkConsentPage` (TR+EN anahtar kelimeler) ile bulunur. Canlıda admin ayarında mesafeli hizmet sözleşmesi seçiliydi; bu durum buraya düşer.
  - Bulunamazsa link gösterilmez.
  - Not: Kodda mesafeli sözleşmeye düşen bir "fallback" yoktu; yanlış yönlendirme admin ayarındaki `consentLegalPageId`'den geliyordu.
- **Canlı destek (`live-chat-widget.tsx`) ve checkout (teslimat adresi KVKK notu):** İkisi de `resolveKvkkNoticePage` kullanıyor. Bu fonksiyon eşleşme bulamazsa **ilk yasal belgeye** (`legalPages[0]`, ör. mesafeli hizmet sözleşmesi) düşüyordu; yanlış metne gitme riski oradaydı. Düzeltme:
  - Fonksiyon artık önce KVKK/aydınlatma (TR+EN), sonra gizlilik arıyor; hiçbiri yoksa `null` dönüyor.
  - Bileşenler zaten `null`'da linksiz düz metin gösteriyordu; bileşen kodu değişmedi.
- **Doktor profili ve randevu onay kutuları** zaten sıkı `resolveKvkkConsentPage` kullanıyordu (Paket A2); değişiklik yok.
